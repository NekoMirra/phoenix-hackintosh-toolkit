## 开机亮度总是满格：定位与修复

**根因**（有日志实证，不是猜测）：
- `log show` 必须用 `/usr/bin/log`（zsh 的 `log` 是内置命令会报错），且读内核日志要 root。
- 开机日志序列：
  - `fb0: panel backlight at 100%`（NVKMS 初始化后硬件就是满格）
  - 3 秒后 `backlight: brightness parameters on AppleBacklightDisplay, logical level 65535/65535`
  → 驱动从 `AppleBacklightDisplay` 拿到 65535 并应用。
- 驱动**会保存但不恢复**：`NVRMFB` 二进制里只有 `nullmoth-backlight` 一个背光相关 NVRAM 变量，没有任何 restore 日志/代码路径。
- macOS 侧也不存：`/var/root/Library/Preferences/com.apple.CoreBrightness.plist` 里只有 Night Shift 的 `CBBlueReductionStatus`，**没有 DisplayPreferences**；`~/Library/Preferences/com.apple.BezelServices.plist` 也没有亮度键。
  → 这块第三方 framebuffer 屏没有任何一方持久化亮度，每次启动按 100% 点屏。

**NVRAM 编码（实测确认）**：`nullmoth-backlight` = `[0x02][u16 little-endian = brightness * 65535]`
- 0.25 → `02 00 40`(0x4000)、0.80 → `02 cc cc`(0xcccc)、0.5047 → `02 34 81`(0x8134)
- 亮度滑块动一下，3 秒内驱动就写回，值精确等于 float×65535。

**修复（用户态补一次恢复）**：

⚠️ **第一版方案失败（15:30 重启实测）**：一次性脚本读 NVRAM → 读到的是 65535。
原因两条，都是后来才查清的：
1. **开机时驱动把 100% 写回了变量**，覆盖掉上一次会话的值（开机 70 秒后读到的就是 65535）；
2. 驱动的写入是**延迟/去抖**的，实测滞后几十秒到几分钟（15:51 实际 0.596，变量还是 0.475）。
   → 这个 NVRAM 变量既会被开机污染、又是滞后的，**不能当持久化来源**。
3. 另外实测：显示器休眠/唤醒不会重置亮度（`pmset displaysleepnow` + `caffeinate -u` 前后都是 0.5956），
   所以只需要防开机那一次覆盖。

**最终方案（常驻守护 + 自己的状态文件）**：
- `~/.local/bin/brightness-daemon.sh`：状态文件 `~/.local/state/brightness-target`；
  启动后 24 秒内连写 8 次目标值（压住 WindowServer 的默认推送），60 秒保护期内偏离即写回，
  保护期后把偏离当成用户改动记录进状态文件。TICK=2s / TOL=0.006，可用 TICK/GRACE/WARM 环境变量调。
- `~/Library/LaunchAgents/local.brightness.restore.plist` 改为 `KeepAlive=true` 常驻跑守护。
- `brightness.c` 新增 `-q`（只输出 float），供守护轮询。
- 实测（TICK=1 GRACE=6 WARM=1）：人为置 0.90 → 守护 8 秒内拉回 0.30；再人为改 0.65 → 保持 0.65 并写入状态文件。
- 旧的一次性脚本改名 `restore-brightness.sh.deprecated`，避免两个逻辑打架。
- `tools/brightness.c` → `~/.local/bin/brightness`：用 DisplayServices 私有 API
  （`DisplayServicesGetBrightness` / `DisplayServicesSetBrightness`）读/写亮度，
  这是唯一可靠的读写途径（`ioreg` 里没有 AppleBacklightDisplay 节点，`VTIsHardwareDecodeSupported` 那类假阴性不适用）。
- `~/.local/bin/restore-brightness.sh`：从 NVRAM 解码 logical → 转 float → 在 0/3/8/16/26s 各写一次（WindowServer 登录后会再推一次默认值，幂等补写）。
- `~/Library/LaunchAgents/local.brightness.restore.plist`：RunAtLoad。

**环境坑（重要，下次别再踩）**：
- 我们这个 shell 里 `launchctl list` 恒为 0 行、`launchctl bootstrap gui/$UID` 报 `5: Input/output error`
  —— 是沙箱假象，**不代表 agent 没加载**。验证方式：看 agent 自己的日志文件时间戳
  （`local.ntfs4mac.automount` 14:44:29 有日志 → 用户级 LaunchAgent 登录时确实会跑）。
- `nvram <var>=...` 写 Apple GUID 变量要 root；用 osascript admin 可以。

## 蓝牙终于通了：BlueTool 一直在按 Broadcom 刷机

连续三轮都判定「软件路径穷尽」，第四次才找到真正的卡点。日志（`process == "BlueTool"`）：

```
BlueTool: USB Bluetooth Host Controller 0xE0D8 Firmware Version v100 BCD Device 0x0100
BlueTool: Could not USB DFU detach for device ... error 0xE000404F
BlueTool: updateFirmwareInSerialFlash res=3
bluetoothd: BlueTool failed to run boot script with result 3
```

`0489:E0D8` 这个伪装 ID 在 macOS 眼里是 Broadcom 系，于是 bluetoothd 去跑「串行 Flash 固件更新」，
这颗联发科芯片当然不响应 DFU detach → 脚本返回 3 → **bluetoothd 直接放弃上电**，
控制器永远停在 `BCM_4350C2 / UART / Address: NULL`（这是占位值，不是硬件信息）。

修法是一个空文件 + 一个之前被误关的 kext：

```sh
sudo touch /etc/bluetool/SkipBluetoothAutomaticFirmwareUpdate
# Kernel/Add 里重新启用 BlueToolFixup 2.7.2
```

冷启动后：`updateFirmwareInSerialFlash res=0`、`Address: 94:BB:43:XX:XX:21`、`State: On`。
完整配方与中间态判据见 [../bluetooth-mt7922.md](../bluetooth-mt7922.md)。

**教训**：`SimpleMtkBtFw` 的 README 说「不要装第二个固件加载器」，指的是 BrcmPatchRAM3；
`BlueToolFixup` 不是加载器，它是负责让 BlueTool 跳过刷机脚本的那一环。我按「避免冲突」把它关了，关错了。

## 麦克风：不是权限，是板载 HDA 被 NullMoth 抢了

先前误解了 TCC 的 `auth_value`（`0`=拒绝，`2`=**允许**）。写授权后实测：
4 秒 192000 个样本，**峰值 0.00000 / RMS 0.00000**，两个 Conexant 设备都是零。

根因：`HDEF@0,6` 上挂的不是 AppleHDA，而是 `NMXAudio`
（NullMoth 附带，`IOPCIClassMatch 0x04030000` + `IOProbeScore 5000`，通吃所有音频类设备）。
它给板载 HDEF 建了输出/输入两套引擎，但输入不接 ADC、不填 DMA → 空壳。
AppleHDA 因为 probe score 低，永远抢不到。

已把 NMXAudio 的匹配收窄成 `IOPCIPrimaryMatch = 0x22be10de`（只认 NVIDIA HDMI 音频），
把 HDEF 让回 AppleHDA + AppleALC + SimpleHDA，**待重启验证**。

## AirDrop：确认做不了，做了三条路线的调研

`ifconfig -l` 没有 `awdl0`、`ioreg -c IO80211Interface` 计数 0 —— MT7922 被暴露成以太网卡，
系统没有 AirPort 接口，AWDL 无从谈起。三条路线：AirportMtkWlan（作者明确写 AWDL ❌）、
Apple `AppleSunriseWLAN.dext`（dext 自带 `IOPCIMatch 0x792214c3` 与 AWDL personality，
但社区卡在「无线电不扫描」）、换 Broadcom 卡。详见 [../open-issues.md](../open-issues.md)。

## diskutil 卡死：根因是旧版 automount 没有超时

`diskutil list` 直接挂住、ESP 挂不上，一度怀疑分区损坏。实际是 NTFS4Mac 的开机脚本里
一个没有超时的 `diskutil unmount` 把 `diskarbitrationd` 拖死了。

`tools/ntfs4mac-automount.sh` 已重写：所有磁盘操作套 `perl alarm` 硬超时，
`diskutil unmount` → `umount` → `diskutil unmount force` 三级降级，
探测到磁盘服务无响应就中止整轮，另加单实例锁与日志截断。
实测 4 个 NTFS 卷 17 秒全部翻成可写。
